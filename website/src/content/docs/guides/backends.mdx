Noev separates programs from quantum hardware through a unified backend interface (`std::backend::Backend`) and declarative **target descriptions**. Programs never inspect whether they are running on a simulator or a QPU; they only see the capabilities declared by the target.

## Built-in backends

- **`ketrs` (default):** local simulator powered by [`ketrs`](https://github.com/Aethar01/ketrs), exposing every engine as a device target:
  - `ketrs` / `ketrs:sv`: adaptive FP64 statevector (real to complex, both levels, up to 30 qubits)
  - `ketrs:sv32`: adaptive FP32 statevector (both levels, up to 31 qubits, half the RAM)
  - `ketrs:mps`: open-boundary matrix product state (circuit level, 30+ qubits; tune via `NOEV_MPS_MAX_BOND` / `NOEV_MPS_CUTOFF`)
  - `ketrs:pmps`: periodic-ring matrix product state (circuit level, unitary + terminal measurements)
  - `ketrs:density`: density matrix simulator (circuit level, up to 14 qubits, unitary + terminal measurements)
  - `ketrs:gpu` / `ketrs:gpu32`: Vulkan GPU statevector (circuit level; requires building with `--features ketrs-gpu`)
- **`export`:** records circuits to OpenQASM 3 or QIR 1.0 files without simulating anything (`noev run --backend=export` or `noev export`).

Select a backend on the CLI or in `noev.toml`:

```bash
noev check prog.nv --backend=target.toml
noev run prog.nv --backend=ketrs
noev build prog.nv --backend=target.toml
```

```toml
# noev.toml
[target]
backend = "ketrs"
```

## Compile-time capability checks

Before running or building, `noev-sema` checks the program against the chosen target's capabilities:

- **Qubit limits:** rejects programs that exceed the target's maximum qubit count.
- **Execution level:** rejects shot-by-shot runs on circuit-only hardware targets.
- **State inspection:** rejects `std::debug::amplitudes` on targets with `read_state = false`.
- **Gate set and foreign calls:** checks whether gates can decompose to the target's native gate set and whether foreign calls occur while qubits are live.

## Managing cached targets

Use `noev target` to list, inspect, and fetch target descriptions:

```bash
noev target list
noev target show ketrs
noev target fetch <backend-spec>
```

## Plug-in backends

Hardware backends are separate packages written in Noev (`impl std::backend::Backend`), Rust, or C/C++ (implementing `include/noev_backend.h`).

A backend implementation is checked by the compiler so it cannot hold or act on live Noev `Qubit` values; it receives compiled `Circuit` values (or gate-level instructions) and returns classical measurement results. Both `noev run` and compiled standalone binaries load plug-in backends dynamically via `--backend` or the `NOEV_BACKEND` environment variable.

See [Runtime and Backends](../../spec/runtime/) for the full backend trait, target schema, and C plug-in ABI.
